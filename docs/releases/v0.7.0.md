# Trust Protocol Interop Lab v0.7.0 — Portable Evidence, Authority Composition & Current-Epoch Revalidation

**Release date:** 2026-09-26

## Summary

v0.7.0 versions the Lab's post-v0.6 transition from a collection of current implementation probes into a more explicit **portable evidence-production layer**. Evidence obligations can cross repository boundaries without losing target, observer, maturity or claim semantics; authority can be tested at the material commitment boundary for both single and collective actors; interoperability preconditions such as cryptosuite capability floors are executable; and current DTG/VTI evidence can be revalidated at a new source epoch without overwriting historical lineage.

The release remains deliberately bounded. It publishes evidence and executable propositions, not certification, standards conformance, deployment security, legal effect, privacy judgment or whole-portfolio assurance.

## Key additions

### Portable human-power pressure evidence

The Lab now has a deterministic runner and machine-verifiable evidence package for four pressure families:

- expanded disclosure;
- correlation expansion;
- refusal/interaction pressure;
- consequential-decision features.

The package includes governed counter-cases and preserves comparison invariants across A/B fixtures. `COMPLETE` means the requested observations are present; `EVIDENCE_REQUIRED` means they are not. The Lab emits observations and derived signals rather than privacy, harm or legitimacy scores.

### Executable DPIP evidence obligations

The Lab can admit `dpip-evidence-obligation/v1` work objects while preserving:

- target revision;
- observer scope;
- required evidence maturity;
- required observations;
- supplier/producer boundary;
- blocker state;
- claim limitations.

Targetless E3+ requests remain `BLOCKED: NO_TARGET`. Governance-only or operator-only evidence is not relabeled as runtime evidence. DPIP retains privacy-judgment authority.

### Task-citation convergence evidence

A deterministic evaluator now separates:

- credential validity;
- exact task citation binding;
- completion/outcome evidence;
- action authority;
- correlation.

Current source characterization is pinned independently from runtime evidence. Unsupported implementation surfaces remain `not-implemented`; unavailable observer surfaces remain `not-observable`. A specification comment or fixture cannot substitute for an executable outcome-evidence path.

### Authority at material commitment

The existing ARA relationship case now includes executable authority-at-commitment vectors for:

- current authority;
- revocation;
- scope;
- absent approval;
- wrong-action approval;
- stale approval;
- unavailable status.

The result distinguishes permit, deny and indeterminate without treating identity, signature or possession as sufficient authority.

### Collective authority

The same authority model now exercises a bounded collective-principal case:

- current 2-of-3 authority permits;
- observed 1-of-3 denies;
- missing threshold/composition-rule evidence is indeterminate;
- stale membership or stale threshold rule denies;
- duplicate participation counts once.

The collective principal remains distinct from its members/controllers.

### Cryptosuite capability-floor interoperability

A dedicated fixture shows that a shared supported cryptosuite is a necessary verification precondition. JCS-only and RDFC-only implementations have disjoint capability sets and cannot verify each other's declared suite.

Unsupported cryptosuite, invalid proof and producer capability mismatch remain distinct. The fixture does not select a mandatory-to-implement suite or claim implementation of EdDSA/JCS/RDFC.

### Proof-required route evidence

The Lab records the current proof-required assessment without flattening two different states:

- dispatcher-wide proof/freshness/replay controls have materially improved;
- route-level bearer divergence remains reachable where operations are still served outside the signed-document path.

Target-native tests are credited as target evidence, not misrepresented as independent implementation evidence.

### 2026-09-24 current-epoch evidence refresh

The Lab revalidated the evidence surfaces required by the RAHP clean-room epoch against pinned current revisions, including:

- Trust Task → credential integration;
- keyed credential replay convergence;
- VAC use-time authorization/binding;
- status A/B correlation;
- policy-discovery A/B correlation;
- retained Trust Task/evidence A/B correlation.

Historical evidence remains lineage only. Current producers must execute at the frozen source or fail explicitly. Producer failure identifies an evidence/adaptation blocker; it does not automatically create an assurance FAIL.

## Governance and claim boundaries

v0.7.0 preserves these rules:

- upstream owns normative semantics;
- source characterization is not runtime execution;
- synthetic evidence is not deployment evidence;
- a passing Lab result is not independent certification;
- the Lab does not issue DPIP privacy PASS/FAIL or RAHP terminal assurance states;
- missing implementation or observation surfaces remain explicit;
- collective/member identity evidence does not itself prove collective authority;
- evidence refresh creates a new source-pinned epoch rather than rewriting historical results.

## Upgrade / use guidance

Consumers citing current evidence should pin the v0.7.0 tag and the specific case/evidence artifact relevant to their proposition. Do not cite the release as a blanket conformance statement.

When a source or implementation changes materially, rerun only the affected evidence producer and preserve the prior epoch as lineage. Cross-repository consumers should retain the exact producer revision, observer surface and claim boundary.

## Known residuals

The release does not close:

- workflow rationalisation work tracked by #191;
- task-citation runtime surfaces not yet implemented/observable;
- genuine independent two-implementation portability where no second implementation exists;
- deployment-level privacy/governance evidence absent from the Lab;
- deferred protected delegated-care external-adopter maturity work (#166);
- external/normative questions owned by their upstream specifications or specialist repositories.

These are explicit future tranches, not hidden release blockers.
